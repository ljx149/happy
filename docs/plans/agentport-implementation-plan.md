设计输入见本计划各节及「远程执行技术路线」评审。验收目标是在手机浏览器创建和控制用户电脑上的 Claude Code 与 Codex 会话。AgentPort 提供账户、配对、同步和中转，Agent 执行及模型凭据留在用户电脑。P0 保持现有运行时、加密协议和 `/v1` 接口形状。外部会话导入、原生客户端、多节点和模型计费留给后续。

## 1. 技术基线与 Web 路线

交付《Web Client 可行性报告》、版本矩阵和端到端记录。CLI 产品改造和 ECS 部署依赖本阶段结论。

1. 从完整 SHA 建立隔离检出。记录 Node、pnpm、Bun、操作系统及目标 ECS 架构。运行 `pnpm install --frozen-lockfile`、`pnpm --filter happy-server-self-host build`、`pnpm --filter happy build`。保留命令、日志、锁文件及产物校验和。用一次性目录和固定测试密钥运行迁移与服务，重启后验证数据和迁移状态。
2. 追查 Web 的候选源码与发布物。以仓库记录、发布工作流、对应版本的包内容和维护方提供的源码为证据。逐个登记来源、SHA 或包版本、许可证、第三方资产和商用修改及再分发条款。预编译产物可用于隔离环境中的兼容性探索。复用决策需要可维护的源码、明确授权和两次干净构建成功。
3. 在同源 HTTPS 测试环境接入候选 Web，验证 SPA 深链接、API、Socket.IO 和附件 URL。检查客户端是否实际采用 `window.__HAPPY_CONFIG__`，以及注入的配置字段、加载顺序和缓存行为。用手机浏览器和两台测试电脑走完新建与恢复账户、配对、daemon 注册、设备列表、创建与继续会话、双向消息、审批与拒绝、断线重连。Claude Code 和 Codex 分别跑一遍。记录附件上传和下载是否可用、密文覆盖范围及是否依赖外部对象存储。
4. 同时验证 Web-only 登录的改动点和 CLI 隔离。用现有 Web 路径或授权的测试夹具跑真实协议。以临时 `HAPPY_HOME_DIR` 检查凭据、settings、机器标识、daemon PID、锁、端口和后台启动路径。验证 API 与 Web 地址同源、浏览器失败可复制 URL、显式登录与首次运行共用路径。此处用测试配置验证，产品默认值在阶段 2 修改。
5. 用浏览器网络日志和 CLI/Server DNS 或出站记录盘点 Happy 官方 Relay、Web、认证、推送、遥测、CDN 等依赖。屏蔽 Happy 官方流量后重复核心链路，按测试场景保留 Agent 厂商必需访问的记录。

### 身份与授权验证

| 维度 | 必须取得的证据 |
| --- | --- |
| 账户与恢复 | 追踪 `authRoutes.ts` 的挑战签名、终端请求和账户请求两组端点。跨浏览器恢复后能读取原加密会话。记录恢复凭据在哪里生成、由谁持有、浏览器清空及凭据丢失后的实际影响。服务端恢复与客户端密钥恢复分别演练。 |
| 终端配对 | 验证临时公钥、加密响应和落盘凭据。覆盖尚未创建请求、拒绝、退出、超时、重复提交、双账户并发授权、授权后重放。轮询与服务端限流一起验证。 |
| 撤销 | 实测删除设备、CLI 登出、旧 token 在 HTTP 和已连接 Socket.IO 上的权限，及主动断开和重连。检查能否通过旧请求再次换取 token。密钥轮换及历史密文可读范围单独记录。 |
| 加密与隔离 | 两个账户交叉尝试读取或操作对方设备、会话、审批、事件、附件。核对服务端存储和日志中哪些字段是明文元数据。用测试标记检查内容、模型凭据、恢复凭据和 token 是否泄漏。 |

源码提示：`authRoutes.ts` 中相关请求可按公钥查找，已授权请求路径会返回 token，路由本身未见按年龄校验。先核查清理任务、令牌校验、事务与撤销路径。若验证出缺口，阶段 3 补最小兼容实现并设为试运营阻断项。客户端等待超时与服务端授权有效期分别验收。

### 阶段出口

- **复用 Web**。确认可获得、可重复构建、许可明确、能维护品牌与配置，并通过完整 P0 功能矩阵。少量兼容修改可进入阶段 2，须列出具体差异和复测方法。
- **自建最小 Web**。若完整候选无可用源码、授权不明或兼容成本过高，先用有明确许可的客户端逻辑及锁定版本协议建立纵切原型。依次打通账户/恢复与终端配对、设备和会话、消息与审批、重连与附件。用真实测试向量校对加密与消息协议，明确 `happy-wire` 已覆盖的 schema 和仍需复用或补齐的客户端逻辑。原型证明关键路径后重估工期。
- **暂缓产品开发**。若两条路线都缺少可验证的协议实现或恢复路径，提交阻断证据与待解决事项。回滚仅清理隔离环境和测试凭据。

## 2. CLI 与 Web 产品改造

- 从锁定版本建立产品开发分支。新增 `agentport` 安装入口并校验发行包名称、升级与卸载行为。在配置初始化前确定 `~/.agentport` 默认目录，约定显式覆盖规则。检查 CLI、自启动、daemon 重启、自身重启和子进程使用同一套目录、可执行文件和设备身份。检查服务注册名称、PID/锁/控制端口与进程发现；模型工具原有用户配置保持其既有语义。
- 成对解析 Server 和 Web 地址，默认均为 `https://agent.xcodex.vip`。覆盖 env、settings 与默认值的优先级，针对半配置或意外跨域给出明确错误或明确推导规则。排查 `desktopAuth.ts`、推送、诊断、连接管理、更新和认证直连中的独立默认地址。
- 在 AgentPort 的入口让 `doAuth` 进入 Web 分支，保留临时密钥交换、失败回退链接及取消逻辑。保留底层移动配对能力和上游兼容路径。检查显式登录、首次启动、daemon 重启、授权后凭据写入、登出和重新配对。
- 按阶段 1 的 Web 路线交付移动工作台。品牌覆盖 CLI 帮助、错误提示、Daemon 用户可见名称、Web 标题、Manifest、favicon、资源与翻译。保留版权及第三方声明。对手机 Safari 和 Chrome 检查窄屏、键盘、审批按钮、防重复提交和后台恢复。移除或禁用非必要官方集成，并记录实际出口流量。

**验收**：独立安装的 `happy` 和 `agentport` 可同时运行。用预置 Happy 状态做回归，验证 AgentPort 的安装、登录、退出和 daemon 重启均不改变该状态。手机可完成完整会话链路，产品 UI 使用 AgentPort 品牌。回滚时把 CLI 与 Web 恢复到版本矩阵中已验证的组合，并保留独立数据目录供排查。

## 3. Self-host Server 与 ECS 预发布

### 启动与持久化

| 配置 | 实施和验证 |
| --- | --- |
| 入口与工作目录 | 以独立 Self-host 包为首选，构建并在目标 Linux 上验证 Prisma 依赖。安装至版本化目录，使用绝对路径调用包内入口。验证 `happy-server migrate` 与 `happy-server serve` 的参数、退出码和包工作目录。迁移作为显式部署步骤，在同一数据目录停止旧服务并备份后执行，确认迁移成功再启动。 |
| 监听与公开地址 | `HOST=127.0.0.1`、`PORT=3005`。配置 `PUBLIC_URL=https://agent.xcodex.vip`，源码中本地文件、附件等地址生成会用到它。以外网真机验证 HTTPS 下载链接与授权。 |
| 数据 | `DATA_DIR=/var/lib/agentport`、`PGLITE_DIR=/var/lib/agentport/pglite`、`DB_PROVIDER=pglite`。核对本地文件实际落点、权限和磁盘挂载。单实例写入。 |
| 静态资源 | 显式设置 `HAPPY_STATIC_DIR` 指向配套 Web 构建。只有客户端确实消费注入配置时才启用 `HAPPY_INJECT_HTML_CONFIG`，注入公开字段。验证静态缓存、更新回滚及未知 API 路径的错误行为。 |
| 密钥 | `HANDY_MASTER_SECRET` 由受保护的环境文件或服务凭据注入，跨重启保持一致。验证恢复使用原密钥。客户端恢复凭据由用户保管。 |

### 接入与安全

1. 先在本地和预发布环境验证。检查 `ecs110-us-raw`（目标 IP `43.110.147.146`）的架构、磁盘、现有站点、80/443 端口占用和证书挑战方式。验证现有代理配置，再用 Caddy 按 Host 反代同一域名的 Web、API、Socket.IO 与附件。限制外部访问后端端口和内部指标，验证公网 DNS、TLS、WebSocket 升级及已有站点健康。
2. systemd 使用专用服务用户、固定工作目录、绝对路径、受控重启与优雅停止。交付可审阅的环境模板、服务单元、Caddy 配置、健康探测和部署运行手册。验证健康检查反映依赖状态，并用外部合成测试覆盖真实登录、同步与审批。
3. 按阶段 1 证据处理配对有效期、原子授权与撤销。把限制施加到实际 HTTP 和长连接路径，按 IP、账号和端点设置合适的预算，为正常轮询保留余量。审计授权与撤销结果、失败和速率异常，避免记录 token、密钥、请求正文、完整配对材料和聊天内容。收紧或禁用推送、遥测及其他未纳入 P0 的官方集成。
4. 备份覆盖 PGlite、本地文件、版本清单和恢复所需的配置。先采用停写或停服务的一致性备份，密钥独立加密保存，验证异地恢复。演练从备份恢复到隔离环境，并用既有测试客户端读取会话和附件。记录耗时及实际数据损失窗口。

**验收**：电脑与手机走不同公网网络，通过自有域名完成两种 Agent 的创建、聊天、审批和继续会话。分别记录 Relay 断线、Server 重启、daemon 重启后的设备回连、会话历史恢复、执行中任务状态。验证本机权限及项目路径约束仍然生效。外网探测确认后端端口与内部指标无暴露。

**回滚**：迁移前记录 Server/Web/CLI 版本、Caddy 与 systemd 配置及备份校验和。兼容迁移可切回上一组产物。遇到不兼容迁移先暂停写入，使用迁移前的数据库、文件与匹配的密钥成组恢复，先保全失败现场并评估迁移后写入的影响。校验健康、配对、同步和附件后恢复流量。代理调整影响现有站点时恢复原配置并逐站检查。

## 4. 商业试运营验收

P0 按受控邀请、小规模单实例试运营规划。以下各项通过并记录负责人和操作手册后开放邀请。

| 门槛 | 验收证据 |
| --- | --- |
| 注册与配额 | 验证邀请或等效注册控制覆盖实际开户路径，同时允许现有用户恢复。对用户、设备、Session、并发、附件大小和总存储设置可执行配额，实测超限行为与清理。 |
| 权限与隐私 | 完成双账号负向矩阵及已撤销设备测试，覆盖 HTTP、长连接、附件和待处理审批。明确密文与明文元数据保留期、账户删除、附件清理、备份自然过期与恢复凭据丢失的用户说明。 |
| 容量 | 按目标 Linux 实例测连接、消息写入、重连峰值、并行审批和附件流量。记录延迟、错误率、写入积压、CPU、内存、磁盘与恢复耗时，按实测容量留余量后确定试运营人数和配额。 |
| 运维 | 对健康、5xx、Socket.IO 断线、磁盘增长和备份失败设置告警。演练升级、回滚、备份恢复、证书续期及支持流程，定下 RPO、RTO 和停止扩招阈值。 |
| 依赖 | 正常和失败场景均核查无 Happy 官方出站请求。保存去敏网络记录、版本矩阵、许可证清单和部署/恢复记录。 |

试运营异常时暂停新邀请并按故障类型限制写入或切回已验证版本。容量接近约定阈值、恢复耗时超标或需要多实例时，启动 PostgreSQL 与共享存储迁移评估，用真实备份验证数据迁移和回滚后另行发布。

## 估算、风险与待决项

- 原设计的 6–13 人日（复用 Web）与 12–26 人日（自建 Web）仅作功能和基础部署的初估。此前评审给出试运营准备额外 3–8 人日。阶段 1 完成后按 Web 缺口、撤销语义、附件路径和实际容量目标重新拆估。
- 优先关闭四类风险。Web 源码/许可由阶段 1 报告关闭，账户恢复/授权语义由协议测试关闭，自托管可用性由目标 Linux 与备份演练关闭，商业规模由容量与配额验证关闭。附件依赖或加密覆盖范围与原设计不一致时，列为产品范围待决项，明确用户可用能力后再验收。
- 上游更新先进入集成分支，重跑配对、远程会话、审批、断线和持久化矩阵。版本清单固定 CLI、Server、Web 及迁移版本，保留可回滚的构建产物。发布前按仓库 `AGENTS.md` 和 release 技能核对分支、工作区与发布流程。
