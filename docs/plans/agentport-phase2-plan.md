# AgentPort 第二阶段开发与隔离上线计划

> 历史计划。当前开发状态、已完成项、待验收项和后续待办以 [AgentPort 开发记录](../agentport-development.md) 为准。文中的旧分支、remote、版本与部署权限只描述当时阶段；执行时以当前会话授权和现场核实为准。

**上线红线：AgentPort 部署、切流和回滚均不得影响任何现有线上服务。** 包括已有站点、API、后台任务、共享数据库和进行中的长连接。短暂中断、请求失败、连接断开和性能退化都不可接受。无法证明变更范围仅限 AgentPort，或无法在不影响任何现有线上服务的情况下撤回，就停止在该服务器上线，改用独立环境。此约束优先于上线日期和复用现有服务器的目标。

**现有服务器环境视为只读。** 不安装或升级宿主机依赖，不改已有服务、进程、配置、环境变量、监听、防火墙、证书或数据，不重启或重载现有共享代理。只允许在已具备条件的独立运行单元、目录、回环端口和独立入口中新增 AgentPort 资源。若接入新域名必须动现有环境，改用独立环境或独立入口。

## 交付范围

以第一阶段已审阅的 `961a46d` 或实际合入后的等效提交为基线，新开第二阶段分支。保留现有 Xcoder 风格和响应式布局。继续使用 Happy Server、CLI、daemon、V2 配对与 `dataKey`；本阶段目标是从网页远程启动 Codex、Claude Code 和 DSH（DeepSeek Harness），处理工具审批，并在新子域名交付可用实例。

先用 Codex 和 Claude Code 验证共用的远程启动与审批，同时做 DSH 的 ACP 可行性验证。DSH 接入与其验收是第二阶段上线门槛。断线补拉必须在上线前验证。设备管理区分「移除设备记录」和「撤销访问凭据」，只有实际撤销通过测试才开放该功能。旧 `legacy` 会话、历史导入、CLI 改名、默认域名和 Web-only CLI 改造保持独立交付。本次联调用明确指定同一私有地址的现有 Happy CLI。

## 任务 1　网页远程新建会话

**实现**

1. 接通现有新建会话入口。读取账户下的设备并显示在线、离线和不可解密状态。只允许选可用设备。选择 Codex 或 Claude Code，输入或选择用户电脑上的项目路径。以 daemon 的实际能力为准，路径校验与执行由用户电脑完成。
2. 对照 `packages/happy-ios/Sources/HappyCore/Machines/MachineActions.swift`、`packages/happy-cli/src/api/apiMachine.ts` 和 Server 的 Socket.IO `rpcHandler.ts`。用第一阶段的密钥解封实现取出**机器**的 `dataKey`，对参数加密，通过已认证的用户 Socket 发出 `rpc-call`，方法为 `<machineId>:spawn-happy-session`。按官方载荷传目录、Agent、目录创建授权等字段。用同一机器密钥解密响应，处理成功、拒绝、离线和未知结果。
3. 若 daemon 要求创建目录，明确显示电脑和完整路径，等待用户确认再提交。启动成功后按返回的会话 ID 进入聊天，等待会话可读后再开放发送。浏览器在等待期间阻止重复点击。对 Codex、Claude 的当前 daemon 路径分别核对幂等语义，勿沿用仅针对 Happy Agent 的 `clientRequestId` 假设。超时且结果未知时先刷新会话列表，禁止自动重试启动。
4. 首条消息与启动分开处理。可在会话创建后显式发送。若实现创建时填写首条消息，使用稳定的 `localId` 单独提交一次，启动与发送失败分别显示。

**验收**

使用隔离账户、在线 CLI/daemon 和可丢弃项目。分别从网页启动 Codex 与 Claude Code，确认进程在选中的电脑运行、工作目录正确、聊天打开对应会话。覆盖设备离线、项目路径错误、新目录拒绝、重复点击、超时及重复通知。另一账户对该机器的 RPC 必须被拒绝。

## 任务 2　网页批准和拒绝工具请求

**实现**

1. 对照 `packages/happy-ios/Sources/HappyCore/Sessions/SessionActions.swift`、`Chat/ChatReducer.swift` 和对应 CLI Agent 的权限处理。用**会话** `dataKey` 解密 agent state 和消息，从真实权限请求中取请求 ID、工具名及可审阅的命令或参数。对未知格式提示不支持。
2. 网页显示「允许一次」「拒绝」。加密官方请求参数，通过 `<sessionId>:permission` 发出会话 RPC。Codex 与 Claude Code 分别核对所需的 `approved`、`decision` 等字段。审批期间停用按钮。最终状态以 daemon/Agent 更新为准，区分已提交、已处理、请求失效、会话离线与结果未知。
3. 处理两个标签页同时审批和请求在点击前已经失效的情况。请求 ID 必须属于当前会话，不以命令文本或列表顺序推断。验收用无害命令，避免为了制造审批而关闭现有保护。

**验收**

Codex 与 Claude Code 分别做一次允许和一次拒绝。允许后命令在目标电脑执行，拒绝后命令不执行。网页显示实际结果。重复审批、过期请求、错误会话、另一个账号均不得造成额外执行。

## 任务 3　同步恢复与设备权限边界

- Socket 重连后沿用 `GET /v3/sessions/:id/messages?after_seq=…` 补拉，按会话及消息 ID 或序号去重。收到序号缺口时同样补拉，并刷新会话状态和待审批请求。单条坏消息有独立提示，后续有效消息继续显示。验收断网、刷新、后台返回、连续发送以及重复通知。
- 核对 `packages/happy-server/sources/app/api/routes/machinesRoutes.ts` 的 `DELETE /v1/machines/:id`。源码确认它会删除机器和相关 access key 并发布更新。是否能中断既有 Socket、拒绝旧 token 的 HTTP 请求和重连、阻止同一凭据重新注册，需分别实测。
- 若已有接口仅能移除设备记录，UI 只可标「移除设备」，且明确其效果；可暂不开放。真正「撤销访问」另提最小服务端变更及安全验收。记录上线适用范围，未通过撤销验证时只允许自用或明确隔离的受控验证环境，不向外部用户开放注册。

## 任务 4　接入 DSH（DeepSeek Harness）

**现状**：本机的 `dsh` 来自 `@deepseek-ai/dsh`，已安装版本的文档明确提供 `dsh --profile acp` 作为 ACP stdio 入口。锁定版 Happy daemon 的启动分支未注册 DSH，Web 增加一个选项无法启动它。Happy CLI 已有 `packages/happy-cli/src/agent/acp/`，可参考现有 Gemini 接入确定可复用的进程与会话逻辑。

1. **可行性验证，可与任务 1–2 并行。** 在配置好 DSH 的测试电脑上，用该机的现有模型配置和临时测试项目，记录 DSH 版本。启动 ACP stdio，核对初始化、会话创建、首条指令、流式输出、工具许可、取消和进程退出。检查日志走 stderr，stdout 保持协议数据。明确哪些能力已实测，尤其是工具批准与拒绝。默认使用 ACP，遇到阻断时先记录能力缺口并评估适配，避免用一次性 headless 命令冒充可持续会话。
2. **接入 CLI/daemon。** 在用户电脑的 Happy CLI 新增稳定的 `dsh` Agent 标识与启动适配，复用 Happy ACP 生命周期和消息转发。检查普通启动与适用的其他启动入口、CLI/daemon 的可执行文件查找、项目路径、权限事件映射和断开清理。以受支持的 ACP 能力为准处理会话继续或恢复。此项是 DSH 运行时接入，不包含 CLI 品牌改造。AgentPort 服务器仍负责中转，DSH 进程和模型配置保留在用户电脑。
3. **接到同一套 Web 交互。** 让 daemon 通告 DSH 可用性和支持能力。Web 在选定设备支持时开放 DSH，复用新建会话表单、聊天和审批。明确提示未安装、未配置、ACP 启动失败及能力不支持；确保原有 Codex/Claude 路径保持可用。
4. **验收与门禁。** 在干净测试项目通过「网页选电脑和 DSH → 本机启动 → 多轮对话及流式输出 → 一次真实批准和一次真实拒绝 → 看到结果」。验证取消、断线恢复及不支持设备的提示。若目标 DSH 版本无法提供或传递审批，作为上线阻断回报，列明版本、复现方式及缺失能力。上线前先用独立联调实例完成这条链路。

### DSH 实现清单

| 位置 | 改法 |
| --- | --- |
| CLI 启动验证 | 在测试项目目录，用隔离的 `HAPPY_HOME_DIR`，把 `HAPPY_SERVER_URL` 和 `HAPPY_WEBAPP_URL` 指向同一个联调实例，配对后运行 `happy acp -- dsh --profile acp`。这是锁定版已有的通用入口，先用它证明能创建 Happy 会话、收发流式消息和转发审批，再写远程启动适配。 |
| `agent/acp/acpAgentConfig.ts` | 为 `KNOWN_ACP_AGENTS` 增加 `dsh: { command: 'dsh', args: ['--profile', 'acp'] }`。沿用 `index.ts` 中已有的 `happy acp` 入口。远程启动的目标 argv 是 `['acp', '--started-by', 'daemon', 'dsh']`，DSH 子进程收到 `['--profile', 'acp']`。在选中的项目目录启动。 |
| `daemon/run.ts`、`daemon/controlServer.ts`、Agent 类型与校验 | 把 `dsh` 加入启动参数和校验，确认 `apiMachine.ts` 的机器 RPC 能把 Agent 原样传到 daemon。普通进程和 tmux 分支共用同一命令映射，避免 tmux 把未知 Agent 默认为 Claude。仅接受固定 Agent 标识和本机受信任的 DSH 可执行文件路径。启动前检查 daemon 环境下能找到 DSH，缺失时返回可操作的错误。 |
| `agent/acp/runAcp.ts` 与 `AcpBackend.ts` | 沿用现有 ACP 握手、会话创建、daemon 就绪回报和 `GenericAcpPermissionHandler`。实际验证 DSH 的工具事件能产生 Happy 待审批项，现有会话 `permission` RPC 能把决定送回 DSH 的对应选项。若 DSH 事件或选项与现有实现不符，只加薄适配；未知选项不自动批准。 |
| Web 新建会话和详情 | 设备端通过现有机器元数据或已核对的能力字段通告 DSH 支持状态。Web 启动载荷发送 `agent: 'dsh'`，仍走加密的机器 RPC。会话类型按现有 ACP 格式解析，DSH 展示名称使用现有元数据中经过验证的标识；缺字段时明确兼容策略，避免因改名破坏旧客户端。 |

**联调顺序**：先用本地通用入口跑通一次批准和一次拒绝，再验证 daemon 能从网页启动同一个 DSH 适配器，最后补能力提示、取消、断线及双账号隔离测试。若通用入口只支持聊天，先抓取脱敏的 ACP 方法名、能力和请求/响应结构，定位是 DSH 没发审批还是 Happy 映射不到。能映射就补适配；DSH 未暴露所需能力时列为上线阻断。自定义模型凭据沿用该电脑的 DSH 配置，Web RPC 不接收或传输模型密钥。

## 任务 5　新子域名部署，现有服务零影响

### 5.1 只读摸底与上线门槛

**接入前必须核对所有可能受影响的线上服务。** 探测范围须覆盖共享入口、依赖和后台任务。任何既有服务缺少可验证基线，或仍有无法解释的共享依赖，当次变更不得进入上线。

由部署方核实已配置服务器的实际入口、代理产品、部署方式、现有监听端口、运行中的服务、已有域名、DNS 归属、证书签发方式及剩余资源。先记录既有站点的健康探测、关键业务路径和代理指标。文档里的 ECS 和 Caddy 是此前候选方案，以现场为准。

候选域名为 `agent.xcodex.vip`。启用前核对显式 DNS 记录、泛解析命中情况、现有路由和证书，确认没有服务正在使用该主机名。若已被占用，保留原记录，另选空闲子域名。只允许新增该主机名及其证书验证所需的独立记录，不改根域、泛解析、现有记录和现有证书配置。

预检须能解释每一项变更及回滚。若必须修改、重载或重启共享代理，替换已有监听，修改默认路由或防火墙，变更宿主机依赖，迁移已有数据库，或资源余量不足，**停止在该主机上线**。在独立主机或独立入口继续验证。

### 5.2 先运行隔离实例，再接入域名

1. 使用版本化制品，记录前端、Server、提交 SHA 和校验值。设置 AgentPort 独立服务账号、服务名、目录、日志、PGlite 数据、凭据文件和备份。比如 `agentport.service`、`/var/lib/agentport`，端口由现场选定未占用的回环端口。迁移只作用于新建 AgentPort 数据库。
2. 对 AgentPort 单独设置内存、CPU、磁盘和日志容量边界，保留既有服务运行余量。先在回环地址启动并验证健康、静态资源、`/terminal/connect` 深链接、HTTP API 和 Socket.IO。设置 `HAPPY_STATIC_DIR` 为本次产物目录，设置 `PUBLIC_URL` 为新 HTTPS 域名。AgentPort 后端端口不对外公开。
3. 在隔离测试入口用临时本地映射或测试域名验证精确 Host 匹配、TLS 和 WebSocket。生产证书可独立预签时先预签。若证书签发必须等新域名的 DNS 生效，先在隔离入口验证签发流程，再仅为新主机名新增 DNS，保持 AgentPort 业务访问受限。公网证书验证通过后才开放测试访问。只在 AgentPort 的独立入口添加新域名和证书。先验证新入口的配置差异与回滚方案。已有代理、Host、证书、代理目标、默认站点与绑定地址保持原样。变更前后用同一组探测比较现有服务，兼顾进行中的连接。
4. **阿里云 DNS 由部署方自行配置。** 在服务器上通过已有的阿里云 CLI 或凭据配置读取现有 AK/SK，先确认目标域托管在阿里云、当前身份具备必要权限，并只读核对精确记录名、类型、目标和是否冲突。用阿里云 DNS 仅新增 AgentPort 专用子域名记录及必要的专用证书验证记录，记录新增记录 ID、值和 TTL。AK/SK 仅供服务器本地工具使用，严禁打印、复制出服务器，或写入仓库、日志、应用环境和交付文档。权限不足、记录冲突或需要修改既有记录时停止，禁止覆盖、提权或更换现有凭据。按预检确认的证书流程发布新域名记录。从另一网络验证 TLS、首页、终端配对、WebSocket、新建会话、审批和断线恢复。首次只开放给指定测试人员，用独立账户和测试项目。访问限制要覆盖 Web、API 和 Socket.IO，并验证未授权访问确实被拒绝。验证后提供准确的访问 URL、配置位置和当班负责人。

### 5.3 监控与回滚

**切流和回滚都要遵守零影响红线。** 在接入和观察期间持续检查现有服务。任一异常即停止 AgentPort 上线，执行预先演练过的隔离回滚。即使恢复成功，本次变更仍记为未通过，重新排查后才能再次申请上线。

- 接入前为每个受影响服务列出探测项、基线范围、观察窗口、停止阈值和负责人。持续检查既有站点的关键请求、错误率、延迟及预先建立的长连接，同时观察主机资源。任一现有服务出现异常、资源超出预设阈值或监测中断，立即撤回 AgentPort 接入，暂停上线并保留诊断记录。
- 先用预先验证的方式隔离新 Host，使其只得到受控拒绝或 AgentPort 独立入口的停用响应，再停止 AgentPort 服务并撤销本次新增 DNS。DNS 缓存可能继续指向服务器，保留只针对新 Host 的拒绝规则，直到缓存影响消退且确认移除规则不会落到既有默认站点。若 AgentPort 独立入口变更异常，只恢复该入口的原有效配置。预检必须证明恢复路径对缓存中的新 Host 同样安全。阿里云 DNS 回滚按记录 ID 仅撤销本次新增记录。回滚后复测旧 Host 仍由原站点处理。
- AgentPort 本身回滚用上一版制品。若有不兼容迁移，只恢复 AgentPort 自己的一致性备份和匹配密钥。演练停掉 AgentPort 后现有服务仍通过基线探测。

## 完工回报

**最终验收以现有线上服务零影响为前提。** 逐项提供变更前、变更中和变更后的证据。若任何服务发生中断、错误、断连或性能退化，或证据不足，结论为未通过。

- PR 与提交 SHA、涉及的 UI、协议调用、测试命令及通过或跳过项。分别给出自动化协议测试和真实电脑上的 Codex、Claude Code、DSH 结果，并列出 DSH 版本和验证过的 ACP 能力。
- 上线提交、访问域名、AgentPort 独立服务与数据目录、端口和回滚步骤。附现有服务变更前后的探测对照、AgentPort 的外网链路证据和回滚演练结果。凭据不得进入交付记录。
- 有任何共用入口或资源隔离条件不满足时，回报具体阻塞、可复核证据及独立环境方案。现有服务无影响是上线条件，不能以 AgentPort 页面已打开替代。
